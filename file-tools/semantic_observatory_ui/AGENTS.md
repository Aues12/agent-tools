# AGENTS.md

## semantic_observatory_ui

### Purpose

`semantic_observatory_ui` is the visual exploration layer of the Agent Tools ecosystem.

Its responsibility is to present semantic structures generated by upstream tools in a form that is easy for humans to observe, navigate, and understand.

The UI is not the source of truth.

All semantic information originates from upstream systems:

```txt
semantic_ast
    ↓
semantic_cards
    ↓
semantic_observatory_pipeline
    ↓
semantic_view
    ↓
semantic_observatory_ui
```

The UI visualizes semantic structures.

It does not generate, modify, reinterpret, or replace semantic data.

The local API server may accept uploaded Python source and call
`semantic_observatory_pipeline`.

In that flow, the UI still consumes generated semantic artifacts. The browser
does not perform semantic analysis itself.

---

## Primary Goal

Transform semantic information into an explorable observatory.

Users should be able to:

* Navigate between general and specific concepts.
* Explore relationships between semantic entities.
* Inspect semantic cards.
* Follow call graph connections.
* Observe structural patterns.
* Zoom between abstraction levels.

The UI should support understanding rather than information density.

---

## Design Philosophy

### 1. Semantic First

Visual elements must serve semantic understanding.

Avoid decorative UI that does not improve comprehension.

Meaning comes first.

Presentation follows meaning.

---

### 2. Bounded Units

Semantic cards are the primary visual unit.

Each card should represent a clear and limited semantic entity.

Avoid large information walls.

Prefer multiple connected cards over a single oversized card.

---

### 3. Progressive Disclosure

Do not display all information at once.

Users should discover detail gradually.

Typical flow:

```txt
Overview
    ↓
Card
    ↓
Detail
    ↓
Source
```

---

### 4. General ↔ Specific Navigation

Navigation between abstraction levels is a core requirement.

Users must be able to move:

```txt
General
    ↓
Specific
```

and

```txt
Specific
    ↑
General
```

without losing context.

---

### 5. Observatory Perspective

The UI should behave like an observatory.

Users observe structures.

Users do not read long reports.

Prefer:

* maps
* trees
* cards
* clusters
* relationships

over large text blocks.

---

## Initial Scope (v1)

The first version should remain intentionally simple.

### Required

* Semantic card rendering
* Card grid view
* Card detail panel
* JSON data loading
* Search
* Filtering

### Not Required

* Force simulation
* Physics engines
* 3D rendering
* Complex animations
* Graph databases
* Realtime collaboration

### Data Sources

Input data is expected to be generated externally.

Examples:

```txt
cards.json
call_graph.json
semantic_tree.json
```

The UI should consume data.

The UI should not generate semantic structures.

For local development, `server.py` exposes:

```txt
POST /api/analyze
```

This endpoint accepts uploaded Python source content and returns
Semantic Observatory analysis data produced by `semantic_observatory_pipeline`.

---

## Component Philosophy

Components should remain small and composable.

Preferred structure:

```txt
components/

SemanticCard/
CardGrid/
CardDetails/
SearchBar/
Sidebar/
```

Avoid large monolithic components.

---

## Semantic Card Principles

A card should answer:

1. What is this?
2. Why does it exist?
3. How does it relate to other entities?

A card should not attempt to display everything.

If content grows too large:

Create another card.

---

## Visual Style

Preferred characteristics:

* Calm
* Minimal
* Readable
* Structured
* Low visual noise

Avoid:

* Dark fantasy aesthetics
* Excessive glow effects
* Heavy skeuomorphism
* Information overload

The interface should feel closer to a scientific observatory than a dashboard.

---

## Future Observatory Concepts

The architecture should remain compatible with future visualization systems:

* Semantic Trees
* Call Graph Maps
* Observatory Maps
* Quest Trees
* Geometric Views
* Concept Clusters

Do not hard-code assumptions that prevent these future representations.

---

## Success Criteria

The project succeeds when a user can:

1. Open a semantic structure.
2. Understand its high-level organization quickly.
3. Navigate deeper without becoming lost.
4. Move between abstraction levels naturally.
5. Build a mental model of the system.

Understanding is the primary metric.

Visual complexity is not.
