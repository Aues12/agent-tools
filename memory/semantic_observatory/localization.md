# Localization Theory

## [LOC-000] Introduction

Localization Theory begins with a simple observation:

A thing is not identical to any single representation of it.

A city is not its map.

A person is not their photograph.

A program is not its source code.

Every representation reveals something and conceals something.

No representation exhausts the thing itself.

---

## [LOC-001] Localizations

A localization is the manifestation of an underlying pattern within a particular domain.

The same meaning may appear in multiple forms.

For example:

Transmission

may appear as:

* a concept
* a software architecture
* a function name
* a call graph
* a runtime process
* a geometric symbol
* electrical activity

These are not separate realities.

They are different localizations of the same pattern (reality).

---

## [LOC-002] Textual Localization

Source code is a textual localization.

Example:

```python
def send_request():
```

The text provides precision.

The text provides implementation.

The text provides direct control.

However, the text does not immediately reveal the larger structure in which the function participates.

Text is detailed but local.

---

## [LOC-003] Structural Localization

ASTs, call graphs, dependency graphs, and architectural diagrams are structural localizations.

They reveal relationships that remain hidden inside textual representations.

A call graph may show:

* central functions
* orchestration points
* pipelines
* dependencies

that are difficult to perceive directly from source code.

---

## [LOC-004] Geometric Localization

Geometry is a spatial localization.

Geometry does not replace code.

Geometry does not replace architecture.

Geometry reveals patterns through form.

A geometric representation may communicate:

* hierarchy
* balance
* centrality
* flow
* symmetry
* complexity

without displaying a single line of code.

---

## [LOC-005] Runtime Localization

Runtime behavior is a temporal localization.

The same software appears differently when observed through execution.

A function call becomes:

* duration
* sequence
* interaction
* resource consumption

Runtime reveals movement.

Code reveals potential.

Execution reveals actuality.

---

## [LOC-006] Physical Localization

Machine instructions and electrical activity are physical localizations.

Every software system ultimately manifests through physical processes.

The highest abstractions and the lowest implementations are therefore not disconnected realities.

They are different appearances of the same underlying pattern.

---

## [LOC-007] Correspondence

Different localizations are not equivalent.

Different localizations are not interchangeable.

Instead, they correspond.

Text corresponds to geometry.

Geometry corresponds to architecture.

Architecture corresponds to runtime.

Runtime corresponds to physical execution.

No single localization should be privileged as the sole reality.

Understanding emerges from observing the correspondences between them.

---

## [LOC-008] Software Understanding

Traditional software engineering often treats source code as the primary object.

Localization Theory proposes a broader view.

Software understanding is the study of correspondences between localizations.

A programmer should be able to move between:

* text
* structure
* geometry
* execution

while preserving meaning.

This movement is not translation.

It is navigation.

---

## [LOC-009] The Observatory

The purpose of the Semantic Observatory is not merely to store code.

The purpose of the observatory is to observe software through multiple localizations simultaneously.

Semantic Cards, Quest Trees, geometric representations, and runtime views are therefore not separate tools.

They are instruments observing the same underlying reality from different perspectives.
