# Semantic Observatory

## [FND-000] Purpose

Semantic Observatory is a working notebook dedicated to the study of meaning, structure, geometry, software architecture, and their relationships.

It is not a finished theory.

It is a collection of observations, principles, hypotheses, and experiments gathered during the development of Semantic Cards, Quest Trees, and geometry-oriented approaches to software understanding.

The purpose of this observatory is not to preserve conclusions, but to preserve conceptual continuity.

---

## [FND-001] Meaning and Structure

Meaning and structure are not independent realities.

They are different appearances of the same underlying pattern.

A structure without meaning becomes empty form.

A meaning without structure cannot become manifest.

---

## [FND-002] Correspondence (Tekabüliyet)

Meaning and structure do not merely transform into one another.

They correspond to one another.

Different representations may refer to the same underlying pattern while remaining distinct.

Map and territory.

Symbol and referent.

Code and architecture.

Geometry and meaning.

None are identical, yet all may correspond.

---

## [FND-003] Localization

A localization is the manifestation of meaning within a particular domain.

Examples:

* Code is a textual localization of meaning.
* Geometry is a spatial localization of meaning.
* Runtime behavior is a temporal localization of meaning.
* Machine instructions are a computational localization of meaning.
* Electrical activity is a physical localization of meaning.

No localization exhausts the whole meaning.

Each reveals a particular aspect.

---

## [FND-004] Software as Localization

Software should not be understood solely as text.

Source code, ASTs, call graphs, semantic cards, runtime behavior, and machine execution are all different localizations of the same underlying architecture.

The task of software understanding is therefore not merely reading text, but discovering correspondences between localizations.

---

## [FND-005] Semantic Cards

A Semantic Card is a semantic node that gathers multiple localizations around a single conceptual center.

A card may contain:

* Natural-language descriptions
* Structural relationships
* Source code
* Runtime information
* Geometric representations

The card acts as a meeting point between these views.

---

## [FND-006] Observatory Principle

The purpose of the observatory is observation before systematization.

Observations are recorded before they are elevated into principles.

The observatory therefore remains open to revision, refinement, and discovery.

---

## [FND-007] Layered Knowledge Model

Semantic Observatory should distinguish multiple layers of knowledge.

A useful working hierarchy is:

1. Ontological Layer
2. Epistemic Layer
3. Technical Layer
4. Concrete Layer

These layers should not be collapsed into one another.

Each layer answers a different question.

The ontological layer asks what kind of reality or principle is being expressed.

The epistemic layer asks how knowledge is approached, discovered, transformed, or manifested.

The technical layer asks what role a component performs within a system.

The concrete layer asks where the object appears in an actual artifact.

---

## [FND-008] Ontological Layer

The ontological layer contains the highest guiding principles.

In the current working model, two complementary directions are especially important:

* Hayy: flow, life, movement, emergence, potential, and generative motion.
* Kayyum: form, stability, structure, preservation, and sustained order.

These two directions should be treated as complementary.

Flow without form dissolves.

Form without flow becomes empty rigidity.

A healthy knowledge system preserves movement while giving it stable form.

---

## [FND-009] Epistemic Layer

The epistemic layer describes how knowledge work unfolds.

A simple working cycle is:

1. Discovery
2. Understanding
3. Transformation
4. Manifestation

Discovery asks: what should be seen or found?

Understanding asks: what does it mean?

Transformation asks: how should it be reorganized, translated, compressed, or mapped?

Manifestation asks: how should it be expressed, built, rendered, executed, or made present?

This layer is more general than domain-specific software roles.

---

## [FND-010] Role and Phase

Role and phase are different.

Role is a technical classification.

It answers:

What does this component do inside the system?

Examples:

* Parser
* Builder
* Transformer
* Validator
* Locator
* Explorer
* Aggregator
* Renderer
* Executor

Phase is an epistemic classification.

It answers:

Where does this component sit within the knowledge process?

Examples:

* Discovery
* Understanding
* Transformation
* Manifestation

Many roles may belong under the same phase.

For example:

* Locator and Explorer may belong to Discovery.
* Parser, Analyzer, and Validator may belong to Understanding.
* Transformer and Aggregator may belong to Transformation.
* Builder, Renderer, and Executor may belong to Manifestation.

Role is therefore more domain-specific.

Phase is more general.

A Semantic Card may carry both.
